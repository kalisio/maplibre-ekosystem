Contributing ​

Development ​

Installation ​

IMPORTANT

Before getting started, make sure you have the following prerequisites installed:

  • Node.js >= 20
  • pnpm >= 10
bash
# Clone the repository
git clone https://github.com/kalisio/maplibre-ekosystem.git
cd maplibre-ekosystem

# Install dependencies
pnpm install

Linting ​

bash
# Lint all packages
pnpm lint

# Lint a specific package
pnpm lint:<package>

NOTE

maplibre-ekosystem follows the standardJS style guide for linting and code consistency. By default, standard is called with the --fix option to automatically fix style issues before committing.

Auditing ​

Two tools are available for inspecting the codebase:

bash
pnpm inspect

inspect detects unused files, exports, and dependencies via knip

bash
pnpm audit

audit checks for known vulnerabilities in the dependency tree. See the command reference for more details.

Testing ​

bash
# Test all packages
pnpm test

# Test a specific package
pnpm test:<package>

# Run a single test file
pnpm test:<package> <file>.test.js

NOTE

By default, vitest is called with the --coverage option to automatically compute the coverage. Coverage reports are generated using v8 provider.

Building ​

bash
# Build all packages
pnpm build

# Build a specific package
pnpm build:<package>

NOTE

The generated Vite bundle is automatically linted with publint

TIP

To inspect the size and composition of the generated Vite bundle, run vite-bundle-visualizer:

bash
cd packages/<my-package>
pnpm dlx vite-bundle-visualizer

Committing ​

maplibre-ekosystem follows the Conventional commits specifications which provides a set of rules to make commit messages more readable when looking through the project history.

The commit message should be structured as follows:

<type>[optional scope]: <subject>[optional `breaking`]

Where type must be one of the following:

  • build: changes that affect the build system (external dependencies)
  • ci: changes to our CI configuration files and scripts
  • chore: changes that affect the project structure
  • docs: changes that affect the documentation only
  • feat: a new feature
  • fix: a bug fix
  • perf: a code change that improves performance
  • refactor: a code change that neither fixes a bug nor adds a feature
  • revert: revert changes
  • style: changes that do not affect the meaning of the code (lint issues)
  • test: adding missing tests or correcting existing tests
  • wip: temporary commits for work in progress

Versioning ​

We follow Semantic Versioning for versioning a release. Given a version number MAJOR.MINOR.PATCH, increment the:

  • MAJOR version when adding major evolution leading to breaking changes,
  • MINOR version when you adding backwards-compatible features,
  • PATCH version when applying backwards-compatible bug fixes.

To help enforce these rules consistently, we use Changesets to record changes during development and automatically determine the next package versions.

To bump the project to a new version, run:

pnpm bump

This script runs both:

pnpm changeset
pnpm changeset version

During the interactive changeset step:

  • Select the package(s) affected by the changes,
  • Specify the type of version bump (major, minor, or patch) according to Semantic Versioning
  • Use the changeset description to reference the milestone containing the issues included in the release.

Finally, commit the updated versions and changelogs:

bash
git add .
git commit -m "chore: bump to <new version>"
git push

Releasing ​

To publish the packages to NPM, use:

bash
pnpm release

NOTE

When publishing a tag will be created corresponding to the version defined in the package.json

Extending ​

Want to add a new package or create a new example? The meta-ekosystem project offers convenient commands like k-init-package and k-init-example to quickly scaffold your project.

Submission ​

Report a bug ​

Before creating an issue please make sure you have checked out the docs, you might want to also try searching Github. It's pretty likely someone has already asked a similar question.

Issues can be reported in the issue tracker.

Pull Requests ​

We love pull requests and we're continually working to make it as easy as possible for people to contribute.

We prefer small pull requests with minimal code changes. The smaller they are the easier they are to review and merge. A core team member will pick up your PR and review it as soon as they can. They may ask for changes or reject your pull request. This is not a reflection of you as an engineer or a person. Please accept feedback graciously as we will also try to be sensitive when providing it.

Although we generally accept many PRs they can be rejected for many reasons. We will be as transparent as possible but it may simply be that you do not have the same context or information regarding the roadmap that the core team members have. We value the time you take to put together any contributions so we pledge to always be respectful of that time and will try to be as open as possible so that you don't waste it.
